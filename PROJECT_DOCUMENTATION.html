1. Project Overview

AstroKarmaPath is a cloud-hosted research database for astrological case studies. It runs on the web, is reachable from any device on any network, and requires no software installation on the device you use.

Purpose

The project was built to log real-life events alongside the astrological patterns associated with them. Unlike a static notes app, it maintains relationships between three entities — people, combinations (astrological patterns), and research (case studies of events) — and lets you search across all of them at once.

Key Goals

  • Store birth details of persons in a structured, searchable way.
  • Log astrological combinations as flexible {category, value} patterns.
  • Attach one or more combinations to a real-life event (research note).
  • Support multiple observations of the same event.
  • Allow offline work and paste-based bulk data entry.
  • Keep all data automatically backed up to GitHub.
  • Run entirely on free tiers — no subscription required.

Who it is for

A single researcher (you), using a phone or tablet, working on astrological case studies over long periods. The tool is designed for hour-by-hour use — fast entry, fast search, and no friction when adding small observations.

2. Core Concept

The most important design decision in the project is that Combination and Research represent the same underlying idea, seen from two different angles.

Definition

  • A Combination is an astrological pattern. Example: Jupiter + Saturn + 7th house.
  • A Research is a real-life event. Example: Anemia happened.
  • A Research is a container. It holds an event, a list of persons, and one or more observations.
  • Each observation is a single combination attempt — a pattern tested against the event.
In astrology, one event rarely has a single cause. So a research note can hold many combinations, added one at a time. Later, you look for patterns across similar cases.

Unified Data Model

Both independent combinations and research observations are stored in the same combinations table. The only difference is whether the row carries a research_id:

  • research_id is empty → independent combination
  • research_id is set → observation belonging to a research

This is why the same form appears in both places. When you start from a research, the title is pre-filled with the event name. When you start fresh, you type the title freely.

6. The Unified Form

Both independent combinations and research observations use the same form. The only difference is that the title is pre-filled when entered through a research.

FieldRules
Main title *Required. Short result. Free text. Pre-filled as "Event name #N" from a research.
Ref chartMulti-select pills (D1, D9, D10…). Custom refs added via + button.
Combination slotsLabel + value rows. Add/remove with +/× buttons. Both free text.
DashaRows with level (dropdown: MD / AD / PD / SD / Pratyantar) + lord + date.
Date of eventFrom → To, plus optional time. Single date allowed.
Date of loggingAuto-filled with current date + time. Editable.
PersonsCheckbox list of all people. Inherited from research when applicable.
BodyLarge text area. Multiple paragraphs. The long answer.

Title vs Body

  • Title = short result (e.g. "Bad marriage", "Anemia happened #1")
  • Body = long answer (detailed explanation of what happened)
  • These are two separate fields.

7. Save Behaviour

From a research observation

  • Saved in combinations with research_id set
  • observation_num auto-assigned (1, 2, 3…)
  • First observation becomes is_main = 1
  • All research persons linked automatically
  • Additional persons can be added; original research persons cannot be removed

From an independent combination

  • Saved in combinations with research_id = NULL
  • Title = user-typed result
  • Persons explicitly linked via checkboxes

Overwrite rules (when re-importing data)

  • Person: key = name + dob + location
  • Combination: key = title + observation_num
  • Research: key = event + person + date
  • Independent combos with same title → both saved, distinguished by slots

Delete behaviour

  • Deleting a research → observations become independent combinations (not deleted)
  • Deleting an observation → removes the combination row entirely
  • Deleting a person → unlinks from all combinations and research

8. Search System

Global search behaviour

  • Results appear as a mixed list, ranked by relevance — not grouped by type
  • Each result has a visual chip at the top-right corner:
    P Person  C Combination  R Research
  • Ranking: exact title match → starts-with → contains
  • Within the same score: Research > Combination > Person
  • Search across: title, body, slot values, person names
  • The #N observation numbering is ignored during ranking

Live search (People / Combos / Research pages)

  • Input field autofocuses when the page opens
  • As you type, results update after 200 ms idle
  • A–Z letter buttons for quick jumps
  • JavaScript fetches from /api/*/search endpoints

9. Paste / Import Format

Flexible, systematic, lenient parsing. You paste text, see a preview, confirm to save. Overwrites instead of duplicating.

Example block

person
name: Test Person
dob: 1990-08-14
tob: 06:42
location: Chennai, India
manual coords: 13.0827, 80.2707
tags: cinema, sports
short tags: psycho movies, baseball
notes: notes here

combination
title: Bad marriage
refs: D1, D9
slots:
  Jupiter - Aries
  Saturn - 7th house
dasha:
  MD - Jupiter - 2019
  AD - Saturn - 2021
event date: 20/03/2024 to 15/04/2024
log date: 2026-09-26
body: Long description here spanning
      multiple lines is fine.

research
event: Anemia happened
event date: 20/03/2024 to 15/04/2024
persons: Test Person, Abhishek

observation
title: Anemia happened #1
refs: D1
slots:
  Moon - 6th
  Ketu - 8th
event date: 20/03/2024
body: Severe anemia detected.

Parsing rules

  • Block header: #person or just person (both work)
  • Simple fields: key: value
  • Slots: label - value (dash separator), indented
  • Dasha: level - lord - date (dash separators)
  • Dates: accept many formats (14/08/1990, Aug 14 1990, 1990-08-14)
  • Partial paste allowed — saves whatever fields are given
  • Body continues on indented lines
  • Preview shown before saving

10. Excel / CSV Format

Multi-sheet CSV export with auto serial numbers. Cross-linked by S.No.

Sheet 1 — Persons

S.No | Name | DOB | TOB | Location | Manual Coords | Tags | Short Tags | Notes

Sheet 2 — Research

S.No | Event | Date From | Date To | Time | Person S.No(s)

Sheet 3 — Observations

S.No | Research S.No | Obs Num | Is Main | Title | Refs | Slots | Dasha | Event Date From | Event Date To | Log Date | Body | Person S.No(s)

Sheet 4 — Combinations

S.No | Title | Observation S.No | Research S.No | Refs | Slots | Dasha | Event Date | Log Date | Body | Person S.No(s)

Notes

  • Slots stored as Label-Value; Label-Value
  • Dasha stored as Level-Lord-Date; Level-Lord-Date
  • Dates in YYYY-MM-DD format for Excel compatibility
  • S.No can repeat in foreign key columns (one person in many rows)
  • Import reads all sheets, links by S.No, overwrites on re-import

11. Import / Export Hub

Export options

  • JSON — complete data dump, one file, human-readable
  • CSV (ZIP) — 4 sheets as CSVs, ready for Excel / Sheets
  • Push to GitHub — commits a dated backup to the repo automatically

Import options

  • Paste import — paste text, preview, confirm
  • Upload JSON — restore a previous export
  • Import from GitHub — list and pick a backup from the repo

Auto backup

  • GitHub Actions runs a cron job daily at 20:30 UTC (02:00 IST)
  • It calls /data/export/github on the live app
  • A JSON file lands in backups/YYYY-MM-DD_HH-MM.json in the repo
  • Backups are kept indefinitely (you can prune later if needed)

13. Offline Workflow

Currently the app requires internet because the database is in the cloud. The following are planned for future rounds:

  • Paste importer (already built) — write text in Notes or Excel offline, paste when online
  • Offline queue — saved locally, auto-synced when online (not yet built)
  • Cache last-viewed pages — browse previously opened pages offline (not yet built)
  • Watch folder — drop CSV/JSON into a folder, tap "Sync now" (not yet built)
For now, work offline by writing your entries in the paste format, then paste when you have internet.

14. Hosting Setup

Render

  • Free tier — 750 instance hours per month
  • One web service: astrokarmapath-1
  • Build command: pip install -r requirements.txt
  • Start command: gunicorn app:app
  • Environment variables set: TURSO_AUTH_TOKEN, GITHUB_USER, GITHUB_REPO, GITHUB_TOKEN

UptimeRobot

  • Pings https://astrokarmapath-1.onrender.com every 5 minutes
  • Prevents Render free tier from sleeping after 15 min idle
  • App stays warm — instant load for the user

Turso

  • Free tier — 9 GB storage, 500 million row reads / month
  • Database name: astrokarmapath
  • Region: ap-south-1 (Mumbai)

GitHub

  • Repository: uttamrokzz/Astrokarmapath-1 (private)
  • Stores code, backups, and the daily Actions workflow
  • Triggers Render redeployment on push

15. Maintenance & Operations

Making code changes

  1. Edit the file in Pydroid
  2. Run push_to_github.py
  3. Render rebuilds within 1–2 minutes

Viewing logs

  • Render dashboard → your service → Logs tab
  • Errors appear with full tracebacks

Backups

  • Automatic: GitHub Actions daily at 20:30 UTC
  • Manual: tap Push to GitHub on /data
  • Files land in backups/ in the repo

Redeploying

  • Auto on every push to main
  • Manual: Render dashboard → Manual Deploy button

16. Known Limitations

  • Render free tier sleeps after 15 min idle without traffic — solved by UptimeRobot
  • No persistent file system on Render — file operations go through GitHub API or the phone
  • Daily export runs on the server and commits to GitHub (not to your phone directly)
  • Offline queue not yet built
  • Watch folder not yet built
  • Email export not yet built
  • Re-importing data creates duplicates (overwrite logic not yet fully implemented)
  • Import does not yet support multi-sheet CSV input (JSON import works)
